# Adjacent house numbers as a decision-layer rule

Scope: what published address-matching and record-linkage systems do when an exact house number and an off-by-one (or same-parity off-by-two) candidate are both present, whether "keep the exact address and drop the neighbour" is a published rule, why that rule fails when one reference has several true records, which label-free alternatives dev labels can falsify, and whether any published suppression of adjacent numbers raised a precision-heavy metric with the recall cost stated.

The dev and test pair shares and labelled match rates below are task-supplied measurements (United States, dev → test). They are not independently published and have no external URL. They are used only as inputs to the arithmetic. The test match bit is unknown. Nothing below treats the test excess as decoys.

Task-supplied inputs used below:

- A Source 1 business may match several Source 2/3 records (mean about 3.46). Many of those are true duplicates with typos, not one establishment.
- House number differs by 1: share of pairs 0.47% → 0.77% (all candidates); 0.45% → 1.14% among stage-2 p ≥ 0.5. Dev labelled match rate at p ≥ 0.5 is 0.963.
- Differs by 2 and same parity: 0.46% → 0.77% all; 0.48% → 1.16% at p ≥ 0.5. Dev match rate 0.956.
- One-character typo that is not the neighbour pattern: 2.6% → 3.3% all; 4.6% → 5.2% at p ≥ 0.5. Dev match rate 0.987.
- India barely changes. The excess is in the neighbour levels and is larger inside the confident set.
- A later model emitted about 16k more US pairs that the judge vetoes and about 16k more house-mismatch pairs, and lost about 0.00025 macro F0.5. Those counts are not labels.

## What do address-matching and record-linkage systems do when exact house number and off-by-one are both candidates for the same query? Is "keep the exact and drop the neighbour" a published rule?

### Takeaway

Published systems score exact house agreement as a stronger pairwise level than a numeric or edit difference, and one-result geocoders return a single best address while flagging a neighbour only as an explicit fallback when the requested number is absent. No source found states the decision rule "if one query has both an exact house candidate and a neighbouring-number candidate, delete the neighbour." That deletion is the one-link-per-query assumption used in housing-unit linkage and duplicate-free one-to-one assignment. It is the wrong assumption when one reference has several true records.

### Cited Findings

- Splink comparison levels are discrete, ordered from most similar to least, and evaluated per record pair. The first level that is true sets that pair's gamma. A typical waterfall is exact match, then a weaker similarity, then "all other." Levels are not a rule across the other candidates of the same query. — [Splink, Comparisons and comparison levels](https://moj-analytical-services.github.io/splink/topic_guides/comparisons/comparisons_and_comparison_levels.html)
- Splink ships `AbsoluteDifferenceLevel(col_name, difference_threshold)`: a level that is true when the absolute difference of two numbers is within a threshold. It also ships edit-distance levels (`LevenshteinLevel`, Damerau-Levenshtein). These are separate evidence grades for one pair. The out-of-the-box date-of-birth comparison is the closest shipped waterfall: exact match, then Damerau-Levenshtein distance ≤ 1, then absolute date difference ≤ 1 month, ≤ 1 year, ≤ 10 years, then else. Character-edit evidence and numeric/calendar difference are different levels, each with its own match weight. — [Splink comparison level library](https://moj-analytical-services.github.io/splink/api_docs/comparison_level_library.html); [Splink out-of-the-box comparisons](https://moj-analytical-services.github.io/splink/topic_guides/comparisons/out_of_the_box_comparisons.html)
- Splink deduplication keeps every pair above a probability threshold and clusters them with connected components, because one entity can have many non-identical duplicates. A separate routine, single-best links, restricts a cluster to at most one record from each dataset listed as duplicate-free. Dropping a record because another record is already a definite match can delete the only path to a third true duplicate (A matches B exactly, B matches C fuzzily, A does not match C directly; discarding B loses C). — [Real World Data Science, Splink case study](https://realworlddatascience.net/applied-insights/case-studies/posts/2023/11/22/splink.html); [Splink discussion #3049](https://github.com/moj-analytical-services/splink/discussions/3049); [Splink issue #1231](https://github.com/moj-analytical-services/splink/issues/1231)
- The Fellegi–Sunter decision rule classifies pairs independently and can link one record to many. A maximum one-to-one assignment is a later constraint, used when each file is assumed free of duplicates (Jaro 1989 linear-sum assignment; Sadinle). If that assumption is false, the assignment declares true duplicate pairs to be non-links. Modern mixture-model implementations ignore the constraint during estimation and enforce it only in post-processing. — [Sadinle, arXiv:1601.06630](https://arxiv.org/pdf/1601.06630); [US Census Bureau RRS2024-05](https://www2.census.gov/library/working-papers/2024/adrm/RRS2024-05.pdf)
- USPS defines a complete address as one that can exact-match the current ZIP+4 and City/State files. Delivery Point Validation confirms the primary (house) number that was submitted. Footnote M3 means the primary number is invalid for that street. Footnote TA is the documented primary-number exception: a single trailing alpha may be dropped so that 123B can confirm as primary 123, returned as DPV confirmation S. Neither M3 nor TA rewrites a numeric house number to a neighbour (19 does not become 20). ZIP+4 can be assigned only when the primary number DPV-confirms (Y, S, or D). — [USPS Publication 28 (PDF)](https://pe.usps.com/cpim/ftp/pubs/pub28/pub28.pdf); [GrayHair, CASS footnotes M1/M3/TA](https://grayhairsoftware.com/cass-certification-explained-what-those-codes-really-mean/); [Google Address Validation, USPS DPV](https://developers.google.com/maps/documentation/address-validation/handle-us-address); [USPS CASS Technical Guide, Cycle O (PDF)](https://postalpro.usps.com/mnt/glusterfs/2023-09/CASS%20Tech%20Guide%20Cycle%20O.pdf)
- Publication 28 / ZIP+4 range logic is parity-aware containment, not nearest-number substitution. A numeric range contains numbers of the coded odd/even indicator between low and high. A number outside the range does not match. Alphanumeric ranges do not match pure numerics. — [USPS Publication 28, Appendix E12](https://pe.usps.com/text/pub28/28ape_003.htm)
- Census TIGER address ranges are potential ranges: every number of a given parity between the low and high, even when no structure exists. The usual coding puts odd numbers on one side of the street and even numbers on the other. A gap can be real, because a missing number may sit on a different edge. Odd/even reversals and out-of-sequence addresses exist as data errors. The Census Geocoder matches a submitted house number to a MAF/TIGER range and interpolates a point. It does not assert that house N and house N+1 are the same unit. Ties (more than one range) are returned as ties, not resolved by deleting a neighbour. — [TIGER/Line Shapefiles technical documentation, Chapter 4 (2009 PDF)](https://www2.census.gov/geo/pdfs/maps-data/data/tiger/tgrshp2009/TGRSHP09C4.pdf); [Census Geocoder user guide (PDF)](https://www2.census.gov/geo/pdfs/maps-data/data/Census_Geocoder_User_Guide.pdf)
- Esri locators, when the parity field is mapped (Even=1, Odd=2, Mixed=3), match a house number only if it agrees with the range parity. Range 44–48 then matches 44, 46, and 48, not 45 or 47. "Match out of range" is a spatial fallback: if the number is outside the segment but within a tolerance, the point is placed at the end of the nearest segment and typed `StreetAddressExt`. It is not an entity-resolution choice between two businesses at adjacent numbers. — [Esri Community, odd/even house matching (staff reply, 2026)](https://community.esri.com/t5/arcgis-pro-ideas/applying-odd-even-logic-when-matching-to-house/idi-p/1702478); [Esri, Tips for improving geocoding quality](https://pro.arcgis.com/en/pro-app/latest/help/data/geocoding/tips-for-improving-geocoding-quality.htm)
- Precisely/Spectrum match code `Hhhh` means "the house number was changed." Extended match-code digits separately flag "house number changed or ignored." The US geocoding guide says false positives occur when the geocoder finds the street but a different house number, if house number is not required, and recommends requiring both house number and street as the close-match criteria. A Spectrum US API guide states that `GeocodeUSAddress` does not change the house number on the output address; inexact house-number candidates are returned only if `KeepMultimatch=Y`, and those candidates use match codes beginning with `H`. — [Precisely, US geocoding match codes](https://docs.precisely.com/docs/sftw/precisely-apis/main/en-us/webhelp/apis/Geocode/ResultCodes/US_Geocoding/GeocodingMatchCodes.html); [Spectrum 2020.1 Enterprise Geocoding Guide for the United States (PDF)](https://docs.precisely.com/docs/sftw/spectrum/20.1/en/pdf/Spectrum_2020.1.0_Geocoding_USA.pdf); [Spectrum 12.0 SP2 Geocoding USA API (PDF)](https://docs.precisely.com/docs/sftw/spectrum/12.2/en/pdf/Spectrum_12.0.SP2_Geocoding_USA_API.pdf)
- HERE returns `matchLevel=houseNumber` both for an exact number and for a neighbouring number when the requested number is not in the map (new build, missing point). The neighbour case is flagged `houseNumberFallback=true`, with `houseNumberFallbackDifference` equal to the numeric gap. In a documented example, requested Ringelsteinweg 11 (not in the data) is returned as 7; the house-number field score is 0.96 rather than 1, described as reduced by 4 points for a numeric distance of 4. HERE's own guidance is that the caller decides whether to accept neighbours and what difference is acceptable. Fallback is what happens when the exact number is absent, not a deletion of a second record when the exact number is present. v7 geocode always falls back to the next closest known number within a predefined maximum distance. — [HERE, Using house number fallback](https://www.here.com/docs/bundle/geocoding-and-search-api-developer-guide/page/topics-api/code-geocode-hsn-fallback.html); [HERE Geocoder, result relevance](https://www.here.com/docs/bundle/geocoder-api-developer-guide/page/topics/scoring.html); [HERE Geocoder, response attributes](https://www.here.com/docs/bundle/geocoder-api-developer-guide/page/topics/resource-type-response-geocode.html)
- Robin Linacre's address-matching note uses Flat A, 24 Jubilee Street versus Flat A, 25 Jubilee Street as the canonical non-match: the strings are almost identical and still must not match. He also rejects the hard rule "if the building number is different, the addresses do not match," because the addresses that are hardest to match are the ones hardest to parse, and a wrong parse makes that rule drop true matches. For confidence he uses distinguishability, the score gap between the best candidate and the second best, because the product is a geocoder: there should be a single canonical address, not many. He reports that deterministic if-trees break on edge cases and that weights should be learned. A worked failure of "require the discriminating token" is a messy "Flat A 10 Station Street" whose neighbour candidates include "9 Station Street" and "Flat A 9 Station Street"; a naive token rule selects the 9. — [Linacre, Building Accurate Address Matching Systems (2025-06-29, updated 2025-06-30)](https://www.robinlinacre.com/address_matching/)
- Census CARRA practice for linking the American Housing Survey to commercial address files blocks on five-digit ZIP and the full house number, so a match is intended to be the same housing unit. The explicit alternative they tested is not "drop the neighbour." It is: block only on the first character of the house number, penalise the remaining characters, and, because exact house agreement is still rewarded, match "201 MAPLE ST" to "201 MAPLE ST" before matching it to "203 MAPLE ST." That preference is inside a one-address-to-one-address search. — [Brummet, CARRA Working Paper 2015-04 (PDF)](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- Peter Christen's *Data Matching* (Springer, 2012) is the standard monograph on field comparison, classification, and one-to-one versus duplicate detection. The book page that would quote a house-number rule is paywalled and was not retrieved. No open Christen source found states "drop the off-by-one candidate when an exact house candidate exists." — [Springer, Data Matching](https://link.springer.com/book/10.1007/978-3-642-31164-2)

### Inferences

- "Exact agreement outranks a numeric difference" is a published pairwise waterfall (Splink levels; Brummet's reward for 201=201 over 201=203; Precisely `S`/`R` codes versus `H`). "Delete the neighbour pair whenever the exact pair is also present" is not that waterfall. The waterfall assigns one gamma to each pair. Both pairs can stay above a match threshold.
- The published place where the second candidate is discarded is one-result geocoding (Linacre's single canonical address; HERE fallback only when the number is missing; Precisely multimatch opt-in) or one-to-one linkage of files assumed to contain no duplicates (Jaro / Sadinle / Splink `cluster_using_single_best_links`). Both assume the second record is an alternative hypothesis for the same entity, not another true copy.
- US street numbering makes `|diff|=1` and `|diff|=2` with the same parity different physical relations. TIGER and Esri put opposite parities on opposite sides, so a difference of 1 is typically across the street and a same-parity difference of 2 is the next number on the same side. A one-character substitution of the last digit (12→13) is both a keystroke error and a parity change. A non-edit numeric neighbour (19→20, two characters) is a weaker typo and a stronger "next building" signal. Systems that separate edit distance from absolute difference (Splink's date waterfall is the template) are distinguishing those, not deleting one because the other exists.
- USPS-style matching is the opposite of fuzzy neighbour acceptance: the submitted primary number must confirm, or the address is invalid (M3). The only primary-number rewrite found is dropping one trailing letter (TA), which keeps the numeric stem. That does not support treating ±1 as the same establishment, and it also does not support deleting a separately observed ±1 record that is itself a real delivery point.

### Gaps

- No retrieved Splink document ships a house-number comparison whose levels are exact / ±1 / ±2. Users can build that waterfall from `ExactMatchLevel`, `AbsoluteDifferenceLevel`, and `LevenshteinLevel`. Whether any production Splink model does so was not found.
- Christen's book was not opened at the field-comparison or classification chapters. A page-level quotation is a gap, not a negative result.
- Precisely's wording is slightly inconsistent across documents ("house number was changed" versus "does not change the house number on the output"). The operational fact that is stable across the docs is that an inexact house number is a distinct, lower match class (`H`), not a silent substitute for an exact.
- No source was found that studies the joint case "exact candidate and ±1 candidate are both in the candidate list for the same query, and more than one of them can be a true duplicate."

## Why is "keep the exact, drop the neighbour" dangerous when the labelled match rate of ±1 is about 0.96 and a reference has several true records?

### Takeaway

The rule treats an exact house record and a neighbouring-number record as mutually exclusive answers to one query. The task is not that problem: one Source 1 has on average about 3.46 Source 2/3 records, and on dev a confident off-by-one pair is a labelled match 96.3% of the time. Dropping the neighbour because the exact record exists therefore drops a true typo-duplicate in the typical labelled case, not a rare false positive. The 0.963 figure is marginal, not conditional on an exact co-candidate; that conditional rate is the quantity that can overturn the warning, and it has to be measured on dev.

### Cited Findings

- On the task's own dev labels, among stage-2 pairs with p ≥ 0.5, house numbers that differ by 1 have labelled match rate 0.963 and are 0.45% of those pairs. Same-parity difference of 2 has match rate 0.956 and is 0.48% of those pairs. One-character typos that are not the neighbour pattern have match rate 0.987 and are 4.6% of those pairs. (Task-supplied; not an external source.)
- Brummet states the one-unit assumption in words: blocking on the full house number is "important for assuring that successful matches represent the same housing unit," and "120 RED RIDGE RD" versus "121 RED RIDGE RD" are "certainly different housing units." The same paper's preference for 201 over 203 applies when the matcher must pick one commercial address for one survey address. — [Brummet, CARRA WP 2015-04](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- Linacre states the one-result assumption in words: "There should be a single match — we do not want to match a single messy address to multiple candidate addresses." Distinguishability is a confidence measure for that single choice, not a licence to delete other true copies. — [Linacre, Building Accurate Address Matching Systems](https://www.robinlinacre.com/address_matching/)
- Splink's own deduplication write-up says clustering is used precisely because each person may have many duplicates, and issue #1231 shows that keeping only one of two definite matches drops transitive true matches. — [Real World Data Science, Splink case study](https://realworlddatascience.net/applied-insights/case-studies/posts/2023/11/22/splink.html); [Splink issue #1231](https://github.com/moj-analytical-services/splink/issues/1231)
- Sadinle: the no-duplicates-within-file assumption is what implies maximum one-to-one linkage. The Fellegi–Sunter rule does not enforce it. Enforcing it when the assumption is false produces conflicting, and wrong, non-links. — [Sadinle, arXiv:1601.06630](https://arxiv.org/pdf/1601.06630)
- F-measure, precision, and recall summarise a confusion matrix. The same F can come from different precision/recall mixes, so a tiny movement in a precision-heavy F does not identify which pairs were wrong. — [Hand and Christen, Consistently Evaluating Record Linkage Classifiers, JDIQ](https://dl.acm.org/doi/10.1145/3786768)

### Inferences

- Failure mode, stated as a record pattern. Source 1 record R is a real business at 19 Main. Source 2/3 contains both a clean copy at 19 Main and a one-digit typo at 18 or 20 Main (or a same-parity neighbour such as 17 or 21). Both copies are true duplicates under the task definition (mean multiplicity about 3.46). The proposed rule ranks exact above ±1 above ±2 and emits only the exact. The typo copy is a false negative. Nothing about the typo pair's own score matters once a better-addressed sibling exists. That is a recall failure, not a tie-break.
- Marginal arithmetic, dev, p ≥ 0.5, if the entire off-by-one slice were dropped. This is an upper bound on how many pairs the rule can touch, not an estimate of the rule, which only drops neighbours that co-occur with a better address. Share of confident pairs = 0.45%. Labelled match rate = 0.963.
  - True positives removed, as a share of confident pairs: 0.0045 × 0.963 = 0.004335, about 0.433% of confident pairs.
  - False positives removed: 0.0045 × (1 − 0.963) = 0.0001665, about 0.0167% of confident pairs.
  - Labelled true pairs removed per labelled false pair removed: 0.963 / 0.037 ≈ 26.0 to 1.
- Same bound for same-parity difference of 2. Share 0.48%, match rate 0.956.
  - True positives removed: 0.0048 × 0.956 = 0.004589, about 0.459% of confident pairs.
  - False positives removed: 0.0048 × 0.044 = 0.000211, about 0.021% of confident pairs.
  - Ratio ≈ 21.7 labelled true pairs removed per labelled false pair removed.
- The one-character-but-not-neighbour slice is both purer (0.987) and an order of magnitude larger (4.6% of confident dev pairs versus 0.45%). Any rule that accidentally includes those pairs, for example by treating every Levenshtein-1 house string as a neighbour, multiplies the recall damage. 12 versus 13 is both `|diff|=1` and a one-character substitution. 19 versus 20 is `|diff|=1` and Levenshtein 2. 9 versus 10 is `|diff|=1` and a one-character insertion. The task's 0.963 bucket mixes these. The marginal 26-to-1 ratio therefore mixes keystroke duplicates with possible true neighbours.
- Why the marginal rate is not the rate that applies to the rule. Two effects push the conditional match rate, given that an exact-house co-candidate of the same name exists, in opposite directions. (1) If the exact record already is the establishment, the neighbour is more likely a different door, so the conditional match rate falls below 0.963. (2) If true duplicates are common and a frequent typo is a one-digit house error, the exact copy and the ±1 copy co-occur on purpose, so the conditional rate stays near 0.963. Which effect wins is not in the marginal table. Using 0.963 as if it were the conditional rate overstates or understates the damage; it cannot be signed without the dev cross-tab in the next section.
- Precision of the kept set rises only if the dropped slice is less pure than the current predicted-positive set. A slice whose labelled match rate is 0.963 raises precision only when operating precision is already above 0.963. The neighbour slice is slightly less pure than the non-neighbour one-character slice (0.963 versus 0.987), but both are high. Overall precision of the p ≥ 0.5 set was not supplied, so a precision gain is not established. Under F0.5 (β = 0.5, so precision is weighted more than recall in the β-weighted harmonic mean), removing 26 true pairs to remove 1 false pair is still a recall-dominated change. Macro F0.5 averages across classes, so a slice that is under half a percent of confident pairs can move the headline metric by very little while deleting most of the typo-duplicates of the businesses that have them. The reported loss of about 0.00025 macro F0.5 from a model that added house-mismatch pairs is the same order of insensitivity. It does not identify those pairs as false, and the prompt says not to assume they are.
- Test enrichment is real and is not a label. Inside p ≥ 0.5, the off-by-one share goes from 0.45% to 1.14% (about 2.5×) and same-parity off-by-two from 0.48% to 1.16% (about 2.4×). The non-neighbour one-character share goes from 4.6% to 5.2% (about 1.13×). All-candidate shares rise less (0.47% → 0.77% for off-by-one). India barely changes, so the shift is US-specific and concentrated in the confident neighbour levels. US parity makes those levels the cross-street and same-side neighbour relations. That pattern is compatible with more true adjacent businesses in the US candidate generator, more numeric typos, or more non-matches. The test match bit cannot separate them. Fitting a drop rule to "explain" the test rise would, on dev, be aimed at a slice that is 96% labelled matches.

### Gaps

- The conditional labelled match rate of a ±1 pair given that the same Source 1 also has an exact-house, same-name candidate was not in any retrieved paper and was not in the task tables. Until it is computed on dev, the 26-to-1 figure is a marginal upper-bound illustration, not the rule's error ratio.
- The share of Source 1 entities that have both an exact and a neighbour candidate was not supplied, so the number of pairs the proposed rule would actually drop is unknown. It is at most the whole 0.45% (off-by-one) or 0.48% (same-parity off-by-two) of confident dev pairs.
- Overall precision and recall of the p ≥ 0.5 set were not supplied, so the sign of the precision change and the F0.5 change cannot be computed, only bounded by the slice size.
- No count was supplied for how often a neighbour pair is also a one-character edit. The split is a dev calculation, not a literature number.

## Is there a safer rule that does not need test labels, and what can dev labels falsify before an upload?

### Takeaway

Three label-free gates are safer than "exact beats neighbour" because each fires on a narrower event than "an exact copy exists." None should be uploaded on the marginal 0.96 match rate. Each has a dev cross-tab that can kill it: the labelled match rate inside the pairs the rule would suppress. If that rate stays near 0.96, the rule deletes true duplicates. Test labels are not required for that check, and the test excess must not be used as a substitute.

### Cited Findings

- Splink already separates a one-character edit level from a numeric or calendar difference level, and assigns each its own weight rather than deleting the weaker pair. Match weight is supposed to fall as the level gets less similar; two levels with the same weight should be merged. — [Splink out-of-the-box comparisons](https://moj-analytical-services.github.io/splink/topic_guides/comparisons/out_of_the_box_comparisons.html); [Splink match weights chart](https://moj-analytical-services.github.io/splink/charts/match_weights_chart.html)
- Brummet's tested relaxation still prefers the exact house number when both the exact and the off-by-two are available ("201" before "203"), and he treats 120 versus 121 as different housing units even though they are one digit and one character apart. That is evidence about housing-unit linkage, not evidence that a one-character house typo is a non-match in a duplicate-record task. His paper also says false-match prevalence cannot be known without truth data. — [Brummet, CARRA WP 2015-04](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- HERE exposes neighbour acceptance as a caller policy (`houseNumberFallback`, difference), not as an automatic drop, and only when the requested number is missing. — [HERE, result relevance](https://www.here.com/docs/bundle/geocoder-api-developer-guide/page/topics/scoring.html)
- Linacre's conclusion, after listing neighbour and token rules that look decisive and then fail, is that learned weights beat a tree of deterministic suppressions. — [Linacre, Building Accurate Address Matching Systems](https://www.robinlinacre.com/address_matching/)
- The later model's extra US pairs are described as judge-vetoed and as house-mismatch pairs (about 16k each) with a macro F0.5 change of about −0.00025. The task statement says not to assume those pairs are false. (Task-supplied.)
- TIGER/Esri parity: opposite parity is the other side of the street when parity is coded. A same-parity difference of 2 is the same-side step. Mixed parity (Esri value 3) disables that constraint. — [TIGER/Line Chapter 4 (PDF)](https://www2.census.gov/geo/pdfs/maps-data/data/tiger/tgrshp2009/TGRSHP09C4.pdf); [Esri Community, parity field](https://community.esri.com/t5/arcgis-pro-ideas/applying-odd-even-logic-when-matching-to-house/idi-p/1702478)

### Inferences

Rule A — down-weight ±1 only when two Source 1 entities both claim neighbouring numbers of the same name.

- What it does. It does not fire because one reference has an exact copy and a typo copy. It fires when two reference entities already occupy the two neighbouring numbers under the same name, so a Source 2/3 record at one number can be cross-linked to the other reference. That is a competing-claim gate, not a best-address gate.
- Why it can still be wrong. The two Source 1 rows may themselves be duplicates of one business, or a common name may collide on a common street. Then the gate suppresses true links.
- What dev labels falsify, before any upload. Restrict to stage-2 pairs with p ≥ 0.5 and `|house difference| = 1` (and, separately, same-parity difference of 2). Split into (a) a second Source 1 of the same name owns the other number, versus (b) only one Source 1 is involved. Report labelled match rate, pair count, and labelled true-positive count in each cell. If (a) stays near 0.96, do not suppress: the "two references" are not functioning as two establishments. If (a) falls well below the operating precision of the p ≥ 0.5 set and (b) stays high, the gate is supported on dev, and the upload note must still state how many labelled true pairs in (a) would be dropped. Also stratify (a) by name frequency; a high match rate only among rare names means the gate is mostly a common-name collision. No test label is required. Do not tune the threshold on the US test excess.

Rule B — emit a ±1 (or same-parity ±2) pair only if the judge also agrees.

- What it does. It treats the judge as a second filter on the neighbour levels only. It does not drop a neighbour merely because an exact sibling exists.
- Why it can still be wrong. The judge may be the component that already dislikes house-number mismatch. Gating on it then re-applies that dislike. The about 16k judge-vetoed US pairs and the about 16k extra house-mismatch pairs are not labelled false, and a −0.00025 macro F0.5 does not make them false. They may be the same pairs or overlapping pairs; the task lists both counts and does not say they are identical.
- What dev labels falsify. On dev only, cross-tab judge agree versus judge veto against the label, inside p ≥ 0.5, for `|diff|=1`, for same-parity `|diff|=2`, and for the one-character non-neighbour cell (dev match rate 0.987) as a control. If vetoed neighbour pairs are still mostly labelled matches, the judge is not a precision filter for this pattern and the gate fails. If vetoed neighbour pairs have a much lower labelled match rate than agreed neighbour pairs, and the control cell shows the judge does not veto ordinary one-character typos at the same rate, the gate is supported. Report the labelled true-positive count among vetoed neighbour pairs, not the 16k test-side count. A dev match rate near 0.96 inside the veto cell falsifies the gate even if the judge is confident.

Rule C — keep every ±1 or same-parity ±2 pair whose house numbers are a one-character edit; suppress only absolute-difference-1 pairs that are not one-character edits (19 versus 20, 29 versus 30, 99 versus 100), and optionally same-parity difference-2 pairs that are not one-character edits (18 versus 20, 28 versus 30).

- What it does. It follows the Splink separation of edit evidence from numeric difference. A single insertion or substitution (12/13, 9/10, 100/101, 12/14) stays. A two-character numeric step that happens to be a difference of 1 or 2 (19/20, 18/20) is the only suppression candidate. It does not require an exact sibling, so it does not delete a typo-duplicate just because a clean copy is also present.
- Why it can still be wrong. Brummet's 120 versus 121 is a one-character difference and he still calls the units different. In the other direction, the task's whole neighbour bucket is 96.3% labelled matches, so the non-edit subset may still be mostly true duplicates (transpositions are not the only typo; a wrong digit plus a carry, or a dropped digit that changes two characters, can be a real duplicate). Census housing-unit practice must not be imported as a prior that overrides this task's dev labels.
- What dev labels falsify. Split dev p ≥ 0.5 pairs by numeric difference (1, versus 2 with the same parity, versus other), by parity change, and by Levenshtein distance on the house-number string (1 versus greater than 1). For each cell report share of confident pairs, labelled match rate, and labelled true-positive count. Suppress a cell only if its match rate is materially below the operating precision of the p ≥ 0.5 set. If the Levenshtein-greater-than-1 and `|diff|=1` cell is still around 0.95 or higher, Rule C is falsified and should not ship. Also compute the interaction the original rule cares about, inside each edit cell: labelled match rate when an exact-house same-name candidate for the same Source 1 exists, versus when it does not. If the "exact also present" cell stays near the marginal 0.963, the original keep-exact-drop-neighbour rule is falsified on dev even for the non-edit subset.

Checks that apply to all three rules, still using only dev labels:

- Bound the headline metric before upload. Maximum false pairs removed, as a share of confident dev pairs, is (share of confident pairs the rule touches) × (1 − labelled match rate in that cell). For the entire off-by-one slice that bound is about 0.017% of confident pairs. A macro F0.5 movement on the order of 0.00025 is what a slice this small looks like even under strong assumptions, so F0.5 will not show the recall damage. The quantity to publish internally is the count of labelled true pairs removed, not the macro F0.5 delta.
- Do not use the test rise (0.45% → 1.14% for off-by-one inside p ≥ 0.5, and the matching rise for same-parity off-by-two) as evidence the cell is false. India barely moving, and the rise being larger in the confident set than in all candidates, says the shift is US-specific and score-concentrated. It does not say the extra pairs are non-matches.
- Do not add a test-label lookup, a threshold sweep on test, or a "decoy" interpretation of the 16k judge vetoes as part of the falsification. The falsifiers above are all dev match rates inside the cells the rule would suppress.

### Gaps

- No retrieved system implements Rule A (two reference entities claiming neighbouring numbers) or Rule C (suppress only non-edit numeric neighbours) as a named production rule. They are constructions from the comparison-level and competing-claim ideas above, not citations of a deployed policy.
- Dev match rates inside the proposed cells (two Source 1 claimants; judge veto; Levenshtein greater than 1 and `|diff|=1`; exact co-candidate present) were not supplied. The falsification procedure is specified; the outcome is not known.
- Whether the about 16k judge-vetoed pairs and the about 16k house-mismatch pairs are the same set, a subset, or two different sets was not stated. They must not be added together.

## Is there an empirical result where suppressing adjacent house numbers raised precision under a precision-heavy metric, with the recall cost stated?

### Takeaway

No such result was found. The closest census experiment is the inverse: requiring an exact house number is the high-strictness baseline, and allowing neighbouring numbers raised the share of survey addresses that received a link by a large amount while the author judged many of the new links to be different housing units. That study does not report precision, recall, or F0.5, and it is a one-address-to-one-unit task. The task's own −0.00025 macro F0.5 is not evidence that the extra house-mismatch pairs are false.

### Cited Findings

- Brummet, 2013 American Housing Survey linked to commercial address data, first state, N = 5,325. Production baseline blocks on five-digit ZIP and the full house number. Match rate at the operational cutoff is 78.14%. Blocking only on the first character of the house number, and penalising the other characters, changes that rate as follows (Table 6): cutoff 4.38 (marked as the baseline-like cutoff) 78.40% (+0.26 percentage points versus Table 3); cutoff 2, 78.78% (+0.39 percentage points) with worst-match examples that still look like street-name noise rather than neighbour houses; cutoff 0, 79.77%, worst match "40 E LAKE DR" = "41 E LAKE DR"; cutoff −2, 84.90%, with neighbour examples including 120 versus 121 Red Ridge Rd; cutoff −4, 85.24%, 201 Maple versus 203 Maple; cutoff −8, 85.67%, worst match "2452 WHITE WATER DR" = "2487 WHITE WATER DR". He writes that 120 and 121 "are certainly different housing units," but still a more plausible forced match than "BOAT DR" versus "APPLE DR" if the true address is simply missing from the commercial file. Exact agreement is still preferred when both candidates exist. — [Brummet, CARRA WP 2015-04](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- Same paper, a second state, held out from the cutoff search (Table 9). Baseline match rate 75.83%. System 1 (strip a few bad tokens, block on the first house-number character, cutoff 2) reaches 76.56%, +0.73 percentage points, and the worst matches stay high quality. System 2 (same, cutoff −2), which is defined as allowing "213 MAIN ST" to match "215 MAIN ST", reaches 90.54%, +14.71 percentage points. The author says some new matches look like input junk ("515 MAPLE NONE"), but "the vast majority of the new matches" come from house-number relaxation, with examples "1924 CLEAR WATER BAY RD" = "1927 CLEAR WATER BAY RD" and "3922 WASHINGTON ST" = "3986 WASHINGTON ST". Footnote 15: the majority of the increase from baseline to System 2 is the house-number relaxation, not the street-name errors. The conclusion says a large match-rate gain requires allowing "221 E MAIN ST" to match "223 E MAIN ST", "a match that many analysts may be unwilling to" accept. He states it is impossible to measure the false-match rate without truth data, and that the most important follow-up is truth data. No precision, recall, F1, or F0.5 is reported. — [Brummet, CARRA WP 2015-04](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- Removing penalties on house-number suffix, directionals, and missing fields, while keeping exact house number, moves the match rate only from about 78.14% to 78.16–78.48% (Table 8, house-number suffix row 78.40%). The big lever is the house number itself, not the suffix. — [Brummet, CARRA WP 2015-04](https://www.census.gov/content/dam/Census/library/working-papers/2015/adrm/carra-wp-2015-04.pdf)
- Cayo and Talbot required an exact match on house number, street name, and ZIP before measuring positional error, and geocoded 81% of addresses under that rule (170,819 addresses). They state that using less stringent match criteria would have increased both the match rate and the positional error. They do not report linkage precision or recall for off-by-one house numbers, and the outcome is metres of geocoding error, not duplicate-record F0.5. — [Cayo and Talbot, International Journal of Health Geographics, 2003](https://ij-healthgeographics.biomedcentral.com/articles/10.1186/1476-072X-2-10)
- Smarty's range-versus-point note is about validating one typed address, not about suppressing a second record. On Champa St in Denver they count 2,198 house numbers inside the street's low–high range and 352 real numbers, so range-only validation marks 1,846 nonexistent numbers as plausible. DPV-style confirmation of the actual primary number is their proposed fix. No precision-recall curve for adjacent-number suppression is given. — [Smarty, address false positives](https://www.smarty.com/articles/address-false-positives)
- HERE documents the score penalty for a neighbour fallback (field score 0.96 when the numeric distance is 4 in the worked example) and tells the caller to accept or reject. No precision or recall for a rejection policy is published on that page. — [HERE, house number fallback](https://www.here.com/docs/bundle/geocoding-and-search-api-developer-guide/page/topics-api/code-geocode-hsn-fallback.html)
- Hand and Christen show that one F-measure value is compatible with very different precision/recall mixes, including in large linkage confusion matrices. A precision-heavy F moving by 0.00025 does not identify a precision gain from a particular slice. — [Hand and Christen, JDIQ](https://dl.acm.org/doi/10.1145/3786768)

### Inferences

- Brummet is the right empirical neighbour of this question, and it does not support the proposed rule as a precision upgrade for multi-record duplicates. Reading it in the direction "stricter house number → fewer wrong-unit links" : moving from System 2 back to exact-house blocking would give up 14.71 percentage points of match rate (90.54% → 75.83%) on the second state. He believes most of that 14.71 points are wrong housing units (1924/1927, 3922/3986, 213/215, 221/223). He does not know the false-match rate, because he has no truth data. The recall cost of the strict rule, in his setting, is every survey address whose only commercial counterpart has a miscoded house number. He argues ordinary typos cannot explain the whole gap, because a one-character street typo such as APPEL would have beaten a wrong street name; he does not publish the count of true off-by-one typos among the unmatched.
- That recall cost does not transfer to this task. Brummet assigns at most one commercial address to one survey housing unit. Dropping 203 once 201 is present loses nothing if 203 is a different unit. Here, dropping the ±1 copy once the exact copy is present loses a true duplicate whenever both records are the same business. His "match rate" is closer to "fraction of queries that received a link" than to pair-level recall over a multi-match gold set. A 14.71 percentage point gain in that rate is not an F0.5 result, and the examples he flags as wrong (differences of 2, 3, and 64) are not the same as a one-character typo duplicate.
- At the strict end of his Table 6, allowing neighbours while keeping a high score cutoff buys almost no matches (+0.26 to +0.39 percentage points) and the new worst matches are not adjacent houses. The large match-rate gains appear only after the cutoff is low enough that 40/41, 120/121, and 201/203 are accepted. If this task's confident neighbour pairs are already at labelled match rate 0.96, they are not in Brummet's low-cutoff regime. Suppressing them is not a replay of his strict cutoff.
- No paper found suppressed adjacent house numbers, reported a rise in precision or in F0.5 / F-beta, and stated the recall cost in true pairs lost. Geocoding papers that tighten house-number match criteria report lower match rates and, when they measure it, smaller positional error. Those are not precision-heavy entity-resolution metrics.
- The task's later model (about 16k more judge-vetoed US pairs, about 16k more house-mismatch pairs, about −0.00025 macro F0.5) is not this missing study. The match bit on those pairs is unknown, the judge is not a gold label, and a macro movement that small is what the pair-share arithmetic predicts for a roughly one-percent slice whether the extra pairs are true or false. It must not be cited as a precision gain from suppression.

### Gaps

- No published precision, recall, or F0.5 (or other F-beta) for a rule that drops adjacent house numbers when an exact house candidate is also present.
- Brummet's false-match rate for 201/203 and 120/121 is explicitly unmeasured. The "worst match" examples are clerical illustrations with street names altered for disclosure. They are not a sample of precision.
- Cayo and Talbot do not break out off-by-one house numbers as a class. The statement that looser criteria raise both match rate and positional error is qualitative.
- No result was found for business or establishment duplicates, as opposed to housing units, in which adjacent street numbers were suppressed.
- The task-supplied −0.00025 macro F0.5 has no public source and no pair-level labels. It is recorded here only so it is not mistaken for the empirical result this question asks for.
